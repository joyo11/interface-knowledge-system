The website said 5.34% and 5.39%. Only one is true.

I built a knowledge system over five downloads of Dupaco Community Credit Union's website. It answers with the value that is current, cites the page it came from, reports the copies it rejected, and says plainly when the site doesn't know.

    Step 1 The problem

    Finding an answer is easy. Knowing which one is current is the job.

    Five crawls of the same site over four months. Pages get updated at different times, so for weeks the site contradicts itself. A member asking a bank's AI for a rate must never hear the old number.

    Stale copies

    The rate sheet updates, but the calculator and promo pages keep the old rate.

    60-month auto loan: 5.34% on the calculator, 5.39% on the rate sheet.

    Look-alike facts

    Different terms, tiers and model years are different facts, not contradictions.

    Share Savings pays a different rate at $10,000 than at $25,000. Both are true.

    Things the site never says

    Questions about products that don't exist tempt a system into guessing a nearby number.

    "What's your 7/1 ARM rate?" The right answer contains no number at all.

    Step 2 How it decides

    Five rules, applied in order, every time.

    No model decides what's current. These rules do, so the same question always gets the same answer and every answer can be explained.

    1The date picks the download

    With an "as of" date, answer from the newest download taken on or before it. A date inside the question counts too: "as of May 2026" means May 31.

    2Newest effective date wins

    Every rate table keeps its own "effective as of" date. When copies disagree, the newest date wins and the losers are never quoted. They're reported as conflicts instead.

    3Then the more authoritative page

    Ties go to the page type that owns the fact: rate sheet 5, product page 4, promo or guide 2, calculator or blog 1.

    4Qualifiers are facts, not conflicts

    The question is parsed for term, model year, balance, jumbo, refinance and APR vs APY. Rows that don't match are dropped, so a plain question never gets the jumbo rate.

    5If the site doesn't say it, say so

    No current rate table for that product means a refusal. Refusals contain no numbers, not even a phone number, so there's nothing stale to leak.

    Step 3 How it's built

    About 2,100 lines of plain Python. No packages, no API keys.

    Ingest once, keep history, then route each question to the part of the system that owns that kind of fact.

    Keep every download

    Each snapshot keeps its own view. Identical pages are parsed once. Missing pages carry forward as a last resort.

    • store.py156
    • parse.py330

    Read the question

    Term, model year, balance, flags, metric and any date in the question.

    • qparse.py184

    Pick the current value

    Rates go to the rate tables. Everything else uses stdlib keyword search plus sentence scoring.

    • rates.py377
    • search.py104
    • text.py478

    Answer and report

    Answer with sources and a conflict note, or refuse. Conflicts are listed separately.

    • engine.py214
    • conflicts.py254

    Why no LLM

    One stale number in an answer scored zero. Rules make every answer deterministic, fast and explainable. An LLM could still write the final sentence later, from values already filtered to current.

    Why keep history

    "As of" questions need the site as it stood then, and conflicts only exist when you can compare copies across pages and downloads.

    Why short conflict lists

    Conflicts are scored on precision and recall. Different tiers or rate vs APY are never reported, so the list stays at about 60 real ones.

    Step 5 Limits and what's next

    Where it falls short, and what I'd build next.

    The misses are mostly one kind of question, which makes the next step clear.

    Where it misses

    • Facts spread across paragraphs. "Who is eligible" needs "live or work in the charter area" plus "Iowa, Illinois and Wisconsin". It quotes sentences, so it can't join them.
    • Ambiguous counts. The site gives volunteer-time-off figures for 2023, 2024 and 2025.
    • Written for one credit union. Page types and synonyms like CD and certificate live in two places: parse.page_kind and rates.ALIASES.

    What I'd build next

    • An LLM that only writes the sentence. It gets evidence already filtered to current values, so the stale-value trap stays closed.
    • Per-institution config. Move page types and synonyms into a profile per credit union, so onboarding a new one is configuration, not code.
    • Conflict alerts for the institution. The conflict list is useful on its own: it tells a credit union which of its pages still show old rates.
